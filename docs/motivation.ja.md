# Layerge の目的と解決したい課題

このドキュメントは、Layerge が **なぜ存在するのか** を記録するものです。
API の使い方は [README](../README.md)、個々の設計判断は [design_notes.md](./design_notes.md) を参照してください。

対象読者は、Layerge の開発者・コントリビューター、および「このライブラリを採用すべきか」を判断しようとしている人です。

---

## 1. 前提：Vue Router はページのための仕組みである

Vue Router は「URL とページの対応」を管理する仕組みです。これは正しい設計で、Layerge はそれを置き換えようとはしません。

しかし実際のアプリには、ページではないが**画面遷移として扱いたい UI** が存在します。モーダル、詳細パネル、ウィザード、スタックして重なっていくカード。これらは次の性質を同時に持ちます。

- 画面を覆うので、見た目としてはページに近い
- ブラウザの戻るボタンで閉じてほしい
- URL を共有したら、その状態で開いてほしいことがある
- しかし「ページ」としてルート定義を切るには数が多すぎ、粒度が細かすぎる

Vue Router 単体では、この中間的な存在に対する第一級の扱いがありません。Layerge が埋めようとしているのは、この隙間です。

---

## 2. 解決したい課題

### 2-1. オーバーレイの開閉が履歴から切り離される

素朴に `v-if` と状態管理でモーダルを実装すると、開閉状態は Vue の状態としてのみ存在し、ブラウザ履歴とは無関係になります。結果として次が起きます。

- ブラウザバックでモーダルが閉じず、背後のページごと戻ってしまう
- リロードすると開いていたモーダルが消える
- 「URL を共有したら同じ画面が開く」が成立しない

これを手当てしようとすると、開閉状態と履歴の同期コードがアプリ側に散らばります。**同期コードは必ず破綻します。**競合したとき、どちらが正なのかを決める責任者が居ないからです。

### 2-2. ネストルートで表現するとルート定義が破裂する

では Vue Router のネストルートでモーダルを表現すればよいかというと、今度は別の問題が出ます。

- オーバーレイの種類ごとにルート定義が必要になり、ルートテーブルが肥大する
- ログイン・設定のような「どのページの上にも出したい」オーバーレイを、ルート階層のどこに置くべきか自明でない
- 閉じたときの戻り先が、履歴の状態に依存して一意に決まらない

ルーティングは本来ページの構造を表すものであり、**オーバーレイの開閉という一時的な状態をルート階層に押し込むと、構造と状態が混ざります。**

### 2-3. 非同期処理中の競合で状態が壊れる

ナビゲーションガードが非同期で遅延している最中に、ユーザーが次の操作をすることがあります。ダブルクリック、連打、通信の遅い環境。このとき素朴な実装は次のように壊れます。

- 古い処理が後から完了し、新しい状態を上書きする
- 閉じたはずのオーバーレイが、遅れて到着した処理によって再び開く
- ナビゲーションがキャンセルされたのに、UI 側の状態だけ進んでしまう

これは個々のアプリで都度対処するには難しすぎる問題です。**競合解決の規則はライブラリ側が一貫して持つべきです。**

### 2-4. 閉じるアニメーションが走らない

オーバーレイを閉じた瞬間に DOM を破棄すると、離脱アニメーションを流す時間がありません。かといってアニメーション完了を待つ仕組みをアプリ側に書かせると、`notify*Done` のような呼び出し忘れが必ず発生し、オーバーレイが閉じないまま固まります。

---

## 3. Layerge のアプローチ

上記に対して Layerge は、**ルーターの拡張として**次を提供します。

| 課題 | Layerge の解 |
|---|---|
| 履歴からの乖離 | `push` / `replace` がルーターの履歴と統合され、戻るで閉じる |
| ルート定義の肥大 | ルート定義なしで `open(Component)` / `open(loader)` が使える |
| 戻り先が不定 | `replace` 時に `returnTo` を保存し、閉じると URL を復元する |
| 非同期競合 | **latest-wins** を規則として固定し、古い処理の確定を阻止する |
| 離脱アニメーション | 離脱中も DOM を保持し、`<LayergeTransition>` が通知を自動化する |

ルーターの状態を正とし、オーバーレイをその上の層（layer）として扱う。名前の由来もここにあります。

---

## 4. 明示的な非目標

Layerge が**あえてやらないこと**を明記します。これは機能不足ではなく、設計判断です。

### 4-1. UI を提供しない

z-index、CSS、アニメーション、レイアウトは一切決めません。confirm ダイアログやフォールバック UI もライブラリには含めません。

理由は、オーバーレイの見た目こそがアプリの個性であり、**ライブラリが決めた瞬間に必ず戦うことになる**からです。Layerge は「いつ・どの順で・どの状態か」だけを保証し、「どう見えるか」はアプリに委ねます。

### 4-2. 独自のルーターを持たない

オーバーレイ内で `useRoute()` が別のルートを返すような「独立したルーティング空間」は提供しません。

必要な場合は Vue Router の `createMemoryHistory()` で別インスタンスを立ててください。Layerge が独自ルーターを内包すると、**真実の源が二つになり、同期問題が再発します。**課題 2-1 を自分で作り直すことになるため、これは避けます。

### 4-3. アクセシビリティ属性を自動化しない

`aria-expanded` / `aria-controls` の付与や、トリガー要素の捕捉は行いません。正しい値は UI 構造に依存し、ライブラリからは決定できないためです。

### 4-4. 便利さを理由に公開 API を増やさない

公開 API の追加には常に抵抗します。公開した契約は削除できず、追加のたびにフックの拡張要求を呼び込み、契約が肥大していくためです。

内部的な状態やデバッグ情報は持ちますが、それらは公開状態には昇格させません。

---

## 5. 設計を貫く 4 つの原則

1. **3 状態で説明できること** — 表示挙動は `top` / `stack` / `stack+cache` の 3 つに還元できなければなりません。それ以上の状態は設計が誤っている兆候とみなします。
2. **latest-wins** — 競合したら常に最新の操作が勝ちます。古い処理は `superseded` として確定を阻止します。例外は作りません。
3. **公開契約は小さく保つ** — 公開ステータスは 4 値（`completed` / `aborted` / `failed` / `superseded`）に固定します。内部でより細かく区別していても、公開面には出しません。
4. **何も起きなかったことを説明できる** — 「操作したのに何も起きない」は最も debug しづらい状態です。開発時のみ有効な判断トレースを持ち、なぜ何も起きなかったかを説明できるようにします。

## 6. 他の選択肢との比較

| 手段 | 履歴/URL 統合 | ルート定義の要否 | UI の提供 | 非同期競合の解決 |
|---|---|---|---|---|
| `v-if` + 状態管理 | 自前 | 不要 | 自前 | 自前 |
| Vue Router ネストルート | あり | **必要（肥大）** | 自前 | 部分的 |
| 汎用モーダルライブラリ | なし | 不要 | **あり** | なし |
| **Layerge** | **あり** | 不要 | **提供しない（意図的）** | **あり（latest-wins）** |

Layerge が適しているのは、**オーバーレイの見た目を自前で作りたいが、履歴・URL・非同期競合の面倒は見たくない**ケースです。

逆に、既製のモーダル UI がそのまま欲しいだけであれば、UI を提供するライブラリのほうが適しています。Layerge はその領域を埋めません。

---

## 7. 適用範囲の境界

Layerge を採用すべきでないケースも明記します。

- オーバーレイが 1 種類しかなく、履歴統合も不要な場合 — `v-if` で十分です
- サーバーサイドレンダリング下でのオーバーレイ初期表示を主目的とする場合 — Layerge はクライアント側の履歴を前提としています
- コンテナ内に閉じたオーバーレイ（ページ全体を覆わないもの）が主目的の場合 — `LayergeView` のオーバーレイルートはビューポート基準（`position: fixed`）で、アプリのルートに 1 度だけ配置する設計です
